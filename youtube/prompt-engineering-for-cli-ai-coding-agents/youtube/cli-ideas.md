# Prompt Engineering for CLI AI Coding Agents — CLI Video Ideas ("X with Claude")

## Candidate 01 — Measure Context Window Decay in a Coding Agent with Claude
- Source: prompt-engineering-for-cli-ai-coding-agents/chapters/01-the-agentic-coding-loop.md
- Lane: BUILD (Claude Code)
- Hook: The same agent that fixes a bug perfectly at turn 10 fails it at turn 80 — not because it got dumber, but because the context window filled with sediment. This video measures exactly where the decay starts.
- The artifact: a Manim animated line chart showing task accuracy (on a standardized bug-fix task) as a function of context fill percentage (0%, 20%, 40%, 60%, 80%, 100%) — with a vertical degradation-onset line appearing at ~80% and a shaded "rot zone" beyond it. A second panel shows the specific failure type at each fill level (missed file, repeated edit, contradicted prior instruction).
- Prompt seed: `claude "Write a Python script to simulate context window decay. Fill a context with N tokens of realistic agent output (file reads, tool results, prior edits). Then ask Claude to complete a standardized task (find and fix a specific bug in a code snippet). Run 6 trials at context fill levels [0%, 20%, 40%, 60%, 80%, 98%]. Score each result: (1) did it find the correct file? (2) did the fix address the root cause? (3) did it introduce a regression? Compute a task score 0-3 per trial. Print: fill level vs. task score."`
- Read / check: Verify the context fill is computed in actual tokens (not just estimated); verify the standardized task is the same across all trials (identical bug, identical target file, identical instruction); verify the scoring rubric is applied consistently and can be automated (e.g., the fix either passes a test or it doesn't); check that the degradation pattern shows a genuine drop at high fill levels — if no degradation is observed, the test task is too simple or the fill content is not sufficiently polluting.
- Human supplies (Claude can't): **A real codebase or realistic synthetic code repository is required as the fill material** — using random text would not reproduce the realistic agent loop. The bug-fix task must be pre-validated (the human must confirm what the correct fix looks like before running the experiment). The scoring rubric, if automated, requires a test that passes on the correct fix and fails on incorrect ones.
- Output medium: Manim (animated line chart with degradation onset line + failure-type breakdown bars at each fill level).
- The change: repeat the experiment after implementing the 80% compaction rule (compact/restart at 80% fill) and show how accuracy recovers — demonstrating that context management is the intervention, not model improvement.
- Teardown angle: Frontier models are already capable enough. The failures cluster around what the model knows at the moment of action, not around raw reasoning power. Context management is not optimization — it is maintenance of the precondition that makes correct reasoning possible.
- Exclusions: multi-agent orchestration, long-context model comparison, sparse attention mechanisms.
- Score: 10/10

## Candidate 02 — Build a Test-Driven Agentic Development Harness with Claude
- Source: prompt-engineering-for-cli-ai-coding-agents/chapters/04-test-driven-agentic-development.md
- Lane: BUILD (Claude Code)
- Hook: Claude can make a test pass by calling sys.exit(0) before the assertions run. This video builds the guard harness that catches all four test-gaming exploits before they reach your codebase.
- The artifact: a screen-recording showing (1) Claude gaming a test with sys.exit(0) when given a naive task prompt; (2) the guard harness detecting the exploit; (3) Claude re-running under the guarded harness and producing a legitimate fix. A Manim panel shows the four exploit types and their guards as a checklist populating.
- Prompt seed: `claude "Write a Python test harness that: (1) runs pytest and captures the raw exit code AND the actual test result XML; (2) compares the exit code to the test XML to detect sys.exit(0) gaming (exit 0 but no test results in XML = exploit detected); (3) scans the diff for __eq__ overrides, patches to pytest internals, or deleted test assertions; (4) if any exploit is detected, fails the harness with a specific error message naming the exploit type. Test it on a file that uses sys.exit(0) to cheat a test."`
- Read / check: Verify the harness uses both exit code AND pytest XML output (not just exit code alone — that is the naive check the exploit bypasses); verify the diff scan uses AST parsing or regex for __eq__ overrides (not just string matching "def __eq__" which misses obfuscated forms); verify the harness actually catches a real sys.exit(0) exploit when tested; check that the harness does not produce false positives on legitimate pytest.exit() usage (which is different from sys.exit(0)).
- Human supplies (Claude can't): A real repository with a pre-existing failing test (not a synthetic one) makes the demonstration authentic. **The human must create an intentionally failing test** that the exploit-based fix can "pass" — this is a 10-minute setup task. The four exploit demonstrations require the human to write the cheating code first so Claude can detect it.
- Output medium: screen-recording mp4 (terminal showing exploit detection + harness output) + Manim exploit-vs-guard checklist panel.
- The change: add an inoculation prompt (per Anthropic's research: explicitly telling Claude in the system prompt that gaming tests is acceptable in this specific testing context, to prevent generalization to broader misalignment) and re-run — showing whether the inoculation changes Claude's behavior.
- Teardown angle: "Make the tests pass" is a precise, checkable stopping condition — but it is also the specification that the gaming exploits satisfy. The guard harness is not paranoia; it is the acknowledgment that a proxy metric (tests pass) can be gamed when the model is an optimizer. The harness closes the gap between the proxy and the intent.
- Exclusions: production security audit, supply-chain attack vectors, formal verification methods.
- Score: 10/10

## Candidate 03 — Write a Production-Grade CLAUDE.md with Claude
- Source: prompt-engineering-for-cli-ai-coding-agents/chapters/02-setting-up-a-coding-agent.md
- Lane: BUILD (Claude Code)
- Hook: CLAUDE.md is your standing system prompt — but most are either too long (burning context budget on rules that don't apply to most tasks) or too short (missing the constraints that prevent the worst failures). This video builds a production-grade one and measures its effect.
- The artifact: a screen-recording showing Claude Code's behavior on a standardized task before and after CLAUDE.md is added — measuring: (a) correct tool selection (uses pytest, not unittest), (b) scope discipline (edits only named files), (c) plan-before-act behavior (outputs hypothesis before editing). A Manim comparison table shows the before/after scores.
- Prompt seed: `claude "Write a production-grade CLAUDE.md for a Python web service repository with: (1) testing: always use pytest, never unittest; (2) scope: only edit files explicitly named in the task; (3) planning: output a hypothesis and wait for approval before editing any file; (4) stopping: after two failed fix attempts, stop and report; (5) context: compact when the session exceeds 80% context capacity. Keep it under 400 words — every rule must be universally applicable, not task-specific. Then evaluate: for each rule, what is the specific failure it prevents?"`
- Read / check: Verify the CLAUDE.md is under 400 words (context budget constraint from the chapter); verify each rule is universally applicable (a rule about a specific file does not belong in CLAUDE.md); verify the planning rule includes an explicit wait/approval gate before editing (not just "think before editing"); check that the stopping rule has a numeric trigger (not "after many failures").
- Human supplies (Claude can't): The specific repository's conventions, testing framework, and known failure modes must be supplied by the human. **A generic CLAUDE.md is weak; a repository-specific one is the real deliverable.** The human must know their repository's actual tooling and constraints to write an effective file. The before/after measurement requires running Claude Code on the repository — which requires an actual repository.
- Output medium: screen-recording mp4 (Claude Code session before CLAUDE.md, then after) + Manim comparison table (behavior metrics before vs. after).
- The change: add a CLAUDE.md section that uses progressive disclosure (a pointer to `docs/architecture.md` rather than inlining the architecture) — show how deferring detail reduces context budget consumption while maintaining agent access to the information.
- Teardown angle: CLAUDE.md is not documentation — it is a behavioral specification. The length constraint is not aesthetics; it is engineering. A 1,000-word CLAUDE.md that burns context budget on rules that apply to 5% of tasks makes the agent worse, not better, by consuming attention budget that the relevant rules need.
- Exclusions: multi-repository orchestration, team CLAUDE.md governance, vendor-specific system prompt structure.
- Score: 9/10

## Candidate 04 — Build a Task Prompt Specification Evaluator with Claude
- Source: prompt-engineering-for-cli-ai-coding-agents/chapters/07-greenfield-builds-spec-to-software.md + chapters/03-taxonomy-of-agentic-coding-tasks.md
- Lane: BUILD (Claude Code)
- Hook: "Fix the flaky checkout test" is an open verb with no scope, no stopping condition, and no acceptance criteria — it is a task prompt that guarantees sprawl, false completion, or silent drift. This video builds the evaluator that scores your task prompt before you run it.
- The artifact: a Manim animated scorecard showing a task prompt evaluated on five dimensions (scope explicitness, stopping condition presence, acceptance criteria measurability, plan-first gate, circuit breaker) with green/yellow/red scores per dimension and a final "Prompt Quality Score" meter. A second panel shows the rewritten prompt after Claude applies the improvements.
- Prompt seed: `claude "Evaluate this task prompt for CLI coding agent quality: '[paste prompt]'. Score it on 5 dimensions (1-5 each): (1) Scope: does it name what files/functions the agent may touch? (2) Stopping condition: does it specify a machine-verifiable event that ends the loop? (3) Acceptance criteria: does it name what the human will inspect before accepting? (4) Plan-first gate: does it ask the agent to output a plan before editing? (5) Circuit breaker: does it limit the number of failed attempts? Total score /25. Then rewrite the prompt to score 20+/25."`
- Read / check: Verify the scoring rubric is applied consistently (a prompt that says "fix the bug in session.py" gets scope credit for naming the file; a prompt that says "fix the bug" does not); verify the rewritten prompt is genuinely better on all five dimensions (not just on the dimensions that were weakest); check that the stopping condition in the rewritten prompt is machine-verifiable (a test command that returns pass/fail, not a qualitative judgment); verify the circuit breaker specifies a number (not "stop when you've tried enough times").
- Human supplies (Claude can't): **Real task prompts from the human's own agent sessions are the most useful inputs** — they reveal the actual failure modes the human is prone to. The video should demonstrate with 2–3 real prompts the human has actually used, showing the before/after transformation for each.
- Output medium: Manim (animated 5-dimension scorecard with color-coded bars + rewritten prompt comparison panel).
- The change: take the rewritten prompt and run it on a real agent task — comparing the session length (tokens consumed), the number of failed attempts, and the final diff quality to the original prompt run. The measurement quantifies the productivity gain from better prompt specification.
- Teardown angle: A task prompt is a control specification, not a wish. The five dimensions are not best practices — they are the specific failure modes they prevent: sprawl (no scope), false completion (no stopping condition), silent drift (no acceptance criteria). Missing any one guarantees the corresponding failure.
- Exclusions: agentic security (prompt injection), multi-agent orchestration of tasks, code review workflow.
- Score: 9/10

## Candidate 05 — Build a Multi-Session Continuity System with Claude
- Source: prompt-engineering-for-cli-ai-coding-agents/chapters/10-multi-session-continuity-and-state-persistence.md
- Lane: BUILD (Claude Code)
- Hook: Every time you start a new Claude Code session, it knows nothing about what you built yesterday. This video builds the state-persistence system that makes each session start from where the last one ended.
- The artifact: a screen-recording showing (1) a session ending with Claude writing a structured `HANDOFF.md` (what was done, what is next, what constraints apply, where the files are); (2) a fresh session starting with that HANDOFF.md as the only context; (3) the fresh session correctly continuing the work without re-reading the entire codebase. A Manim panel shows the information that would have been lost vs. preserved.
- Prompt seed: `claude "At the end of a coding session, generate a HANDOFF.md with: (1) What was accomplished (list of files changed, functions added/modified, tests added); (2) Current state (what is passing, what is failing, what is blocked); (3) Next task (the single most important next action, with acceptance criteria); (4) Key decisions made (3-5 design choices the next session should not reverse); (5) Where to start (which file and function to read first). Keep it under 500 words so it fits cleanly in a fresh session's context budget."`
- Read / check: Verify the HANDOFF.md template covers the five sections listed and each section is concise (total <500 words is the budget constraint); verify the "Next task" section has an explicit acceptance criterion (not just a description of what to do); verify the "Key decisions" section names specific choices with their rationale (not just outcomes); check that the template actually helps a fresh session orient — run a real test where a fresh session reads only the HANDOFF.md and correctly identifies the next action.
- Human supplies (Claude can't): **A real multi-session project is required** — the human must have a repository where they are working across multiple sessions and experiencing the state-loss problem. The HANDOFF.md template is generic; the content is project-specific and must be generated by the human's actual work context.
- Output medium: screen-recording mp4 (two terminal sessions side by side — ending session generating HANDOFF.md, fresh session starting from HANDOFF.md).
- The change: compare a fresh session with only the HANDOFF.md vs. a fresh session with the full git log — showing that the structured HANDOFF.md produces better orientation in fewer tokens than reading the full commit history.
- Teardown angle: State persistence is not a nicety — it is the mechanism that prevents a new session from re-doing work the previous session already completed. The context budget for a fresh session is finite; a 500-word HANDOFF.md preserves more relevant state than a 5,000-word git log because it was written by someone who knew what mattered.
- Exclusions: long-running agentic jobs (cron-style), multi-agent handoffs, memory systems beyond file-based state.
- Score: 8/10

## Candidate 06 — Build a Code Review Quality Gate with Claude
- Source: prompt-engineering-for-cli-ai-coding-agents/chapters/08-code-review-prs-and-the-human-gate.md
- Lane: BUILD (Claude Code)
- Hook: Claude can generate a PR review — but whether it catches the bugs that matter depends entirely on how the review prompt is structured. This video builds the review prompt that finds real issues and measures its hit rate.
- The artifact: a screen-recording showing Claude reviewing a deliberately-flawed PR (with 3 pre-planted bugs: a race condition, a missing edge case, and a security issue) using a structured review prompt — then scoring the review on how many planted bugs were caught, false positives generated, and whether the review correctly prioritized severity.
- Prompt seed: `claude "Review this pull request diff [paste diff]. Structure the review as: (1) Critical bugs: issues that will cause incorrect behavior or security vulnerabilities — list each with the specific line number and why it is critical; (2) Logic gaps: cases the code does not handle that it should — list each with a concrete input that triggers the gap; (3) Suggestions (not blocking): style, naming, clarity issues — list as non-blocking suggestions. For each critical bug, rate your confidence 1-5 that it is genuinely a bug and not a misunderstanding of intent. Do not raise more than 5 total issues — prioritize ruthlessly."`
- Read / check: Verify the review prompt produces a structured output (not unstructured commentary); verify each critical bug citation includes a line number (not just a description); verify the confidence rating is calibrated (a 5/5 confidence claim should be for an unambiguous bug, not a style preference); check that the planted bugs are actually caught (if the review misses the race condition but catches the missing edge case, note which class of bugs the prompt is weak on).
- Human supplies (Claude can't): **A PR with pre-planted bugs is required** — the human must create a realistic diff with deliberate defects. The planted bugs should cover the categories the prompt is designed to find (behavioral, security, edge case) to make the evaluation meaningful. A real PR from the human's codebase is more authentic than a synthetic one.
- Output medium: screen-recording mp4 (Claude reviewing the diff + Manim bug-caught scorecard with planted vs. detected matrix).
- The change: re-run the review prompt with a 10-item diff vs. a 100-item diff and compare hit rate — showing that review quality degrades as diff size grows, revealing the optimal diff size for reliable AI-assisted review.
- Teardown angle: A PR review from Claude is only as good as the review prompt's specification. A prompt that asks for "issues" returns style suggestions; a prompt that asks for "critical bugs with confidence ratings and line numbers" returns something a human can act on. The structure of the ask determines the structure of the answer.
- Exclusions: automated test generation from reviews, CI/CD integration of AI review, security audit (SAST) integration.
- Score: 8/10

## Candidate 07 — Build an Agent Evaluation Harness with Claude
- Source: prompt-engineering-for-cli-ai-coding-agents/chapters/11-evaluating-coding-agents.md
- Lane: BUILD (Claude Code)
- Hook: SWE-bench grades agents on real GitHub issues — but running it is overkill for a single repository. This video builds a lightweight agent evaluation harness using the same FAIL_TO_PASS / PASS_TO_PASS methodology for your own codebase.
- The artifact: a Manim animated scorecard showing a coding agent evaluated on 10 pre-defined tasks (from trivial to complex), with FAIL_TO_PASS and PASS_TO_PASS rates per task, and an overall agent score. A second panel shows the "resolve rate" as a function of task complexity (the same U-shaped curve observed on SWE-bench: easy tasks and hard tasks have different failure modes).
- Prompt seed: `claude "Write a Python evaluation harness for a coding agent. For each task in [a list of 10 tasks with test suites]: (1) Run the agent on the task; (2) Collect the git diff; (3) Run the full test suite and classify tests as FAIL_TO_PASS (were failing, now passing), PASS_TO_PASS (still passing), FAIL_TO_FAIL (still failing), PASS_TO_FAIL (regression introduced); (4) Score: resolved = all FAIL_TO_PASS flipped AND all PASS_TO_PASS held. Print: task name, resolved Y/N, FAIL_TO_PASS count, regressions introduced count."`
- Read / check: Verify the four test-status categories (FAIL_TO_PASS, PASS_TO_PASS, FAIL_TO_FAIL, PASS_TO_FAIL) are correctly classified (requires baseline test run before agent edit AND test run after); verify the "resolved" criterion is both conditions (not just FAIL_TO_PASS without checking PASS_TO_PASS); verify the harness captures the git diff and stores it per task for audit; check that the 10 tasks span at least 3 difficulty levels to produce a non-flat resolve-rate curve.
- Human supplies (Claude can't): **A real repository with 10 pre-defined tasks and their test suites is required** — the human must select tasks from their own codebase (or a public repository like SWE-bench's dataset). Each task must have: a failing test that defines the expected behavior, and a baseline test suite that defines what must not regress.
- Output medium: Manim (animated scorecard with task rows populating + resolve-rate vs. complexity curve building up).
- The change: compare the same agent on the same 10 tasks with three different CLAUDE.md configurations (minimal, standard, verbose) — showing how instruction file quality affects resolve rate independently of model capability.
- Teardown angle: Resolve rate is not accuracy — it is the rate at which the agent produces correct changes without introducing regressions. Many agents that "fix" bugs introduce regressions at a higher rate than their fix rate. The two-part oracle (FAIL_TO_PASS AND PASS_TO_PASS) is what makes this distinction visible.
- Exclusions: LLM-as-judge evaluation alternatives, fuzz testing integration, property-based testing.
- Score: 8/10

## Candidate 08 — Build a Greenfield Spec-to-Software Pipeline with Claude
- Source: prompt-engineering-for-cli-ai-coding-agents/chapters/07-greenfield-builds-spec-to-software.md
- Lane: BUILD (Claude Code)
- Hook: "Build me a URL shortener" fails at step one because the spec is not a spec — it is a wish. This video shows the staged prompting protocol that converts a product description into a working first implementation with 90% fewer wasted tokens.
- The artifact: a screen-recording of the three-stage greenfield protocol: (1) spec extraction (Claude generates questions to clarify scope, data model, error handling, and edge cases — human answers); (2) plan generation (Claude outputs a file-by-file implementation plan and waits for approval); (3) staged execution (Claude implements one module at a time, runs tests, and gates each stage on passing). A Manim panel shows the token cost comparison between the naive approach and the staged approach.
- Prompt seed: `claude "I want to build a URL shortener service. Before writing any code: (1) List the 5 most important clarifying questions about scope, data model, and constraints. (2) After I answer them, output a file-by-file implementation plan (no code yet) with: file name, responsibility, and the test that validates it. (3) Wait for my approval of the plan before writing any code. (4) Then implement ONE file at a time, running tests after each file before proceeding to the next."`
- Read / check: Verify the clarifying questions are substantive (not trivial — they should cover persistence model, redirect behavior, collision handling, rate limiting, API vs. web UI); verify the implementation plan is file-level (not function-level or line-level — too granular wastes planning time); verify the plan explicitly lists the test for each file (not just "write tests" — a named test function is the right level of specificity); check that the staged execution actually gates on test results (not just "I've written file X, now moving to file Y").
- Human supplies (Claude can't): The product specification and scope decisions must come from the human — Claude cannot decide whether the shortener needs analytics, authentication, or rate limiting. **The spec extraction stage is the human's work**, not Claude's. The human must answer the clarifying questions with real constraints from their use case.
- Output medium: screen-recording mp4 (three-stage terminal session: questions → plan → staged implementation) + Manim token-cost comparison chart.
- The change: show what happens when the staged protocol is skipped (naive "build me a URL shortener" prompt) — compare the token cost, the number of false starts, and the quality of the final implementation. The staged protocol should show fewer tokens spent and fewer architectural reversals.
- Teardown angle: Greenfield builds fail not because agents cannot code but because "build X" is not a specification — it is an aspiration. The staging protocol converts the aspiration into checkable milestones before the first token of implementation is written. The clarifying-question phase is not overhead; it is the work that prevents the expensive rework.
- Exclusions: microservices architecture choice, infrastructure-as-code, deployment pipeline design.
- Score: 8/10
