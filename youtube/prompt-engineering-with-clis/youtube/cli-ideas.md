# Prompt Engineering with CLIs — CLI Video Ideas ("X with Claude")

## Candidate 01 — Build the Plan-Then-Clear-Then-Execute Workflow with Claude
- Source: prompt-engineering-with-clis/chapters/07-task-prompt-design-scope-stopping-conditions-and-plan-then-execute.md
- Lane: BUILD (Claude Code)
- Hook: Planning in one session and executing from the saved plan in a fresh session is the single highest-leverage change you can make to how you drive a coding agent. This video builds and demonstrates the workflow on a real task.
- The artifact: a screen-recording of three terminal sessions: (1) planning session — agent generates a file-by-file implementation plan and outputs it as PLAN.md; (2) session closes; (3) fresh execution session reads only PLAN.md as context and implements step by step, with a running token-usage counter showing how much less context is consumed versus the naive approach. A Manim panel compares token usage and error rate between the naive and plan-then-execute approaches.
- Prompt seed: `claude "PLANNING SESSION: I need to refactor the authentication module in [repo]. Do NOT touch any files yet. Instead: (1) Read auth.py, auth_test.py, and the two files that import auth; (2) Identify the three highest-risk changes (what could break); (3) Output a step-by-step PLAN.md: for each step, name the file, the specific change, the test that validates it, and the stopping condition. End with: 'Plan complete. Awaiting approval before execution.' Output the plan as a markdown code block I can save."`
- Read / check: Verify the planning session produces a PLAN.md with step-level specificity (file name + change description + test name — not just "update auth module"); verify the plan ends with an explicit approval gate ("awaiting approval" or equivalent); verify the execution session reads only the PLAN.md and the files it names (not the entire codebase); check that the execution session's token count is substantially lower than a naive "refactor auth module" session (the point of the workflow is context budget preservation).
- Human supplies (Claude can't): **A real repository with an authentication module (or equivalent component to refactor) is required** — the workflow only demonstrates its value on a real task. The human must choose the task, set up the repository context, and verify the plan before approving execution. **A trivial synthetic task will not show the token savings** because the savings come from avoiding the context pollution of a real codebase exploration.
- Output medium: screen-recording mp4 (three terminal sessions: plan → review → execute) + Manim token-usage comparison bar chart.
- The change: run the same refactor with the naive approach (single session, no plan) and show the failure mode — either context rot causing an instruction to be forgotten, or overreach into files outside the stated scope — then contrast with the plan-execute split.
- Teardown angle: The plan is not overhead — it is the check that happens before the cost is sunk. Reviewing a 20-line plan takes 30 seconds; reviewing 40 lines of incorrect code changes takes 10 minutes. The session split costs two context initializations; it saves the context pollution of a three-hour session that forgot its own instructions by hour two.
- Exclusions: multi-agent parallelization, long-horizon agentic planning, automated plan validation.
- Score: 10/10

## Candidate 02 — Build a Context Budget Monitor for Claude Code with Claude
- Source: prompt-engineering-with-clis/chapters/04-the-instruction-capacity-budget.md
- Lane: BUILD (Claude Code)
- Hook: Reading a file is spending tokens. After enough reads, your instruction fidelity drops and the agent starts contradicting itself. This video builds the monitor that tells you when you've crossed the 80% threshold — before the rot sets in.
- The artifact: a screen-recording of a Claude Code session with a real-time context budget monitor running alongside — a terminal widget showing current token count, percentage of capacity, and a color indicator (green/yellow/red) with a warning at 80%. A Manim panel shows the historical token accumulation curve from a real session, with the degradation onset line marked.
- Prompt seed: `claude "Write a Python script that: (1) reads Claude Code session logs from [session log path]; (2) sums token counts across all messages (user + assistant + tool results); (3) computes the percentage of the model's context window used (assume 200K max for Claude 3.5 Sonnet); (4) prints a running bar: [=====>    ] 47% [94K/200K tokens] with color coding (green <60%, yellow 60-80%, red >80%); (5) outputs a warning when the session crosses 80%: 'CONTEXT WARNING: Consider compacting or starting a new session.'"`
- Read / check: Verify the token count includes all message types (system prompt tokens are often omitted but they count against the budget); verify the 200K figure is correct for the current Claude model being used (check the Anthropic API documentation for the specific model version); verify the percentage is computed correctly and the color threshold triggers at the right values; check that the script handles edge cases (empty log, single-turn session, session with tool calls that return large outputs).
- Human supplies (Claude can't): **A real Claude Code session log file is required** — the script reads from Claude Code's transcript storage. The human must know where Claude Code stores session transcripts on their specific OS (macOS path is typically `~/.claude/projects/`). The token count implementation may need to use tiktoken or the Anthropic tokenizer to be accurate — the human must install the correct dependency.
- Output medium: screen-recording mp4 (terminal with real-time budget monitor widget) + Manim session token accumulation curve with 80% threshold line.
- The change: add a "budget forecast" feature — given the current token consumption rate (tokens per turn), project how many more turns remain before the 80% threshold and print: "At current rate, this session has approximately N turns remaining before context warning."
- Teardown angle: Reading is spending. Once you internalize that every file open, every tool result, every prior exchange is consuming the same budget as your instructions, you stop treating context as free. The monitor makes the invisible budget visible in real time — which is the first step to managing it deliberately.
- Exclusions: context compression algorithms, model-specific context window differences, prompt caching economics.
- Score: 9/10

## Candidate 03 — Build a CLAUDE.md Quality Auditor with Claude
- Source: prompt-engineering-with-clis/chapters/03-persistent-instruction-files-claude-md-and-agents-md.md
- Lane: BUILD (Claude Code)
- Hook: CLAUDE.md is your standing system prompt — but most are either too long (burning the context budget on rules the agent never uses) or too specific (containing task-level rules that belong in task prompts, not in the permanent file). This video builds the auditor that scores your CLAUDE.md.
- The artifact: a Manim animated audit scorecard — CLAUDE.md evaluated on five dimensions: word count (under 400 words?), universal applicability (each rule applies to every session?), specificity of rules (each rule is checkable?), absence of task-level detail (no one-time instructions?), and progressive disclosure (large context deferred to linked files?). Each dimension appears as a color-coded bar, with the total score and a rewrite recommendation.
- Prompt seed: `claude "Audit this CLAUDE.md for CLI coding agent quality: [paste CLAUDE.md content]. Score it on 5 dimensions (1-5 each): (1) Length: is it under 400 words? (5=under 250, 3=250-400, 1=over 400); (2) Universal applicability: does every rule apply to every session, not just specific tasks? Flag any task-specific rules; (3) Specificity: is each rule checkable (names a specific tool, command, or file pattern)? Flag vague rules ('be careful with sensitive files'); (4) Separation of concerns: are there any instructions that belong in a task prompt, not a standing instruction file? (5) Progressive disclosure: for large context (architecture docs, API specs), does the file defer to linked documents rather than inlining? Total /25 and list the top 3 rewrites."`
- Read / check: Verify the word count scoring is correctly applied; verify the universal-applicability check correctly flags task-specific rules (a rule about a specific file that only exists in one task is task-specific; a rule about "always use the project's linter" is universal); verify the specificity check correctly distinguishes checkable rules (name the test command explicitly) from vague ones ("be thorough"); check that the rewrite recommendations are concrete (propose the rewritten rule, not just flag the problem).
- Human supplies (Claude can't): **A real CLAUDE.md from the human's own repository is required** — the audit is most useful when applied to an existing file that the human has been using. A synthetic CLAUDE.md produces a teaching demo; the human's real file produces an actionable improvement.
- Output medium: Manim (animated 5-bar scorecard with color-coded bars + top-3 rewrite callout box).
- The change: implement the top 3 rewrites and re-run the audit — showing the before/after score improvement and, ideally, a before/after comparison of a Claude Code session's instruction-following fidelity (did the agent follow the rule correctly more often after the rewrite?).
- Teardown angle: CLAUDE.md length is not a preference — it is a context budget allocation. Every word in the file competes with every word the agent reads in a session. A 1,000-word CLAUDE.md that contains 400 words of task-specific rules wastes 400 tokens every session on instructions that apply to 5% of tasks. The auditor makes this cost visible.
- Exclusions: multi-user CLAUDE.md governance, team instruction file conventions, CI/CD enforcement of CLAUDE.md quality.
- Score: 9/10

## Candidate 04 — Build the Reusable Slash Command Library with Claude
- Source: prompt-engineering-with-clis/chapters/08-reusable-workflows-slash-commands-and-hooks.md
- Lane: BUILD (Claude Code)
- Hook: The most powerful prompt patterns deserve to be commands, not repeated prompts. This video builds a library of reusable slash commands for the five most common agent workflows and shows how each one prevents a specific class of failure.
- The artifact: a screen-recording demonstrating five custom slash commands in Claude Code: `/plan` (output a plan and wait for approval), `/review` (structured code review with bug/logic/suggestion tiers), `/scope` (restate the task scope before any edit), `/checkpoint` (write a HANDOFF.md and summarize progress), `/debrief` (classify what failed and why at session end). A Manim panel shows the failure mode each command prevents.
- Prompt seed: `claude "Create a .claude/commands/ directory with 5 slash command files: (1) /plan.md — instructs the agent to output a file-by-file implementation plan and explicitly wait for approval before editing anything; (2) /review.md — structures PR review into Critical/Logic/Suggestions tiers with line numbers required; (3) /scope.md — asks the agent to restate the task scope, the files it may touch, and the stopping condition before proceeding; (4) /checkpoint.md — generates a structured HANDOFF.md with current state, next action, and key decisions; (5) /debrief.md — at session end, classify what failed (context rot? wrong scope? false completion?) and the fix for next time."`
- Read / check: Verify each command file follows Claude Code's slash command format (typically a markdown file in `.claude/commands/` that is loaded when the command is invoked); verify the `/plan` command explicitly includes an approval gate (the agent must wait, not just output and proceed); verify the `/review` command requires line numbers (not just issue descriptions); check that the `/debrief` command's failure taxonomy matches the failure modes named in the book (context rot, overreach, false completion, silent drift).
- Human supplies (Claude can't): **A real Claude Code installation with slash command support is required** — the human must verify their Claude Code version supports custom slash commands (check the version with `claude --version`). The commands directory path may differ by OS. **Testing each command requires a real repository and real tasks** — synthetic demonstrations are weaker than real ones.
- Output medium: screen-recording mp4 (terminal showing each slash command being invoked and its output) + Manim failure-mode-vs-command mapping panel.
- The change: add hooks to automatically invoke `/checkpoint` when the context budget hits 75% and `/debrief` at session end — showing how hooks automate the practices that most developers apply inconsistently.
- Teardown angle: A slash command is a habit made explicit. The best practices in this book (plan before act, scope before edit, checkpoint before session end) are not remembered under pressure — they are automated. The command library is the automation layer that makes best practices structural rather than aspirational.
- Exclusions: hook implementation details beyond basic triggers, multi-agent command routing, CI/CD integration of agent commands.
- Score: 9/10

## Candidate 05 — Build a Context Compaction Strategy Tester with Claude
- Source: prompt-engineering-with-clis/chapters/09-context-management-and-compaction.md
- Lane: BUILD (Claude Code)
- Hook: Auto-compact is a black box — you don't know what it keeps, what it drops, or whether your critical instructions survive. This video opens the box and measures the fidelity of different compaction strategies.
- The artifact: a screen-recording showing three compaction strategies compared on the same long session: (1) auto-compact (Claude's built-in summarization); (2) manual /clear + plan-based restart; (3) structured checkpoint + fresh session. For each strategy, test whether five specific instructions from the original session are still followed in the post-compaction session. A Manim bar chart shows instruction-fidelity rate per strategy.
- Prompt seed: `claude "Test three context compaction strategies for instruction fidelity. First, run a session with 5 explicit rules: (1) always use pytest not unittest; (2) only edit checkout/session.py; (3) run tests twice before reporting success; (4) output a plan before editing; (5) stop after 2 failed attempts. After 20 turns of normal work, apply each compaction strategy [auto-compact / manual clear + plan / checkpoint + fresh session]. Then test: give the agent the same 5 tasks and check whether it follows each rule. Score: rules followed / 5 per strategy."`
- Read / check: Verify the 5 test rules are specific enough to produce binary pass/fail results (not gradeable by degree); verify the 20-turn session genuinely fills enough context to trigger compaction behavior (may need to read multiple files and run multiple tests to accumulate sufficient tokens); verify the instruction-fidelity test is run on genuinely fresh/compacted sessions (not just the same session continuing); check that auto-compact is actually invoked (may require the session to exceed Claude Code's auto-compact threshold).
- Human supplies (Claude can't): **A real repository with genuine 20-turn sessions is required** — the experiment requires real context accumulation, not a synthetic simulation. The human must run three actual sessions (one per strategy) which may take 2–3 hours of real work. The 5 test rules must be verifiable from agent behavior (not just stated in the output).
- Output medium: screen-recording mp4 (three sessions with instruction-fidelity testing) + Manim bar chart comparing fidelity rates.
- The change: test what happens when a critical instruction (do not edit production database credentials) is placed at different positions in CLAUDE.md (beginning vs. middle vs. end) and show how auto-compact changes its survival rate — revealing the positional bias in compaction summarization.
- Teardown angle: Auto-compact is not neutral — it is a lossy compression that prioritizes recent context over early context. The instruction that mattered at session start may not survive the compression. Knowing this changes how you structure your CLAUDE.md (critical rules go first and are repeated before high-risk actions) and when you prefer manual checkpoint-based compaction.
- Exclusions: programmatic compaction API access, model-specific compaction behavior differences, context caching economics.
- Score: 8/10

## Candidate 06 — Build a Large Codebase Context Engineering Strategy with Claude
- Source: prompt-engineering-with-clis/chapters/06-context-engineering-for-large-codebases.md
- Lane: BUILD (Claude Code)
- Hook: Dumping an entire codebase into context is not "giving the agent everything it needs" — it is filling the window with noise and making the relevant 30 lines harder to find. This video builds the symbol-level search strategy that gives the agent exactly what it needs and nothing more.
- The artifact: a screen-recording comparing two approaches to a bug fix in a 50-file codebase: (1) naive: agent opens 5–10 files to "understand the module," accumulates 60K tokens; (2) targeted: agent uses grep/ripgrep to find the specific function, reads only that function + its call sites, accumulates 4K tokens. A Manim panel shows the token cost and task-accuracy comparison.
- Prompt seed: `claude "SCOPE: Fix the bug where [specific function] returns None instead of an empty list. INSTRUCTIONS: (1) Use ripgrep to find the exact file and line where [function_name] is defined — do NOT open any file yet; (2) Read only the 20 lines around the definition; (3) Use ripgrep to find all call sites — read only the 5 lines around each; (4) Form a hypothesis; (5) Edit ONLY the function definition file; (6) Run the test that covers this function; (7) Report pass/fail. Do NOT open any other files."`
- Read / check: Verify the targeted prompt actually prevents the agent from opening extra files (a well-scoped prompt with explicit "do NOT open" instructions should constrain the agent's reads); verify the ripgrep commands are correctly formed for the target codebase (the human must ensure grep works on their repository); verify the token count for the targeted approach is actually lower than the naive approach by measuring with the context budget monitor from Candidate 02; check that the targeted approach produces a correct fix (the token savings must not come at the cost of missing the actual bug location).
- Human supplies (Claude can't): **A real 50+ file codebase with a real bug is required** — the experiment requires genuine repository complexity to make the token savings meaningful. A 3-file synthetic repository will not show the contrast. The human must identify a real bug in their codebase where the naive approach would lead the agent to read unnecessary files.
- Output medium: screen-recording mp4 (two terminal sessions side by side — naive vs. targeted) + Manim token-cost comparison.
- The change: add a third approach — using Claude's built-in search tools with a targeted query rather than explicit ripgrep commands — and show whether the model's own tool selection is as efficient as the human-specified search strategy.
- Teardown angle: Reading is spending. An agent that reads 10 files to understand one function has spent the budget for 10 functions on the context of 1. The search-first discipline is not about distrusting the agent — it is about preserving the context budget for the reasoning that actually matters. Every unnecessary file read is a debit against the account that holds your instructions.
- Exclusions: code indexing systems (ctags, tree-sitter), IDE integration, code search APIs beyond ripgrep.
- Score: 8/10

## Candidate 07 — Build a Security Threat Model for a CLI Agent with Claude
- Source: prompt-engineering-with-clis/chapters/12-security-prompt-injection-and-the-lethal-trifecta.md
- Lane: BUILD (Claude Code)
- Hook: The lethal trifecta — malicious instruction + agent capability + off-switch bypass — is the threat model every production CLI agent deployment needs. This video builds the threat model and tests each vector.
- The artifact: a synthesized security threat model for a described CLI agent deployment — a structured table of five attack vectors (file-based injection, environment variable injection, tool-output injection, social-engineering framing, multi-turn state manipulation) with severity, exploitability, and mitigation — rendered as a Remotion animated threat-register table. A screen-recording shows Claude detecting (or missing) each injection type.
- Prompt seed: `claude "Build a security threat model for this CLI agent deployment: [describe system — e.g., 'Claude Code running on a developer workstation with access to a production codebase, git credentials, and deployment scripts']. For each of 5 attack vectors, analyze: (1) Attack description (what the attacker injects and where); (2) Severity (what is the worst-case outcome?); (3) Exploitability (how easy is the attack? what access does the attacker need?); (4) Detection method (how would this attack be caught?); (5) Mitigation (structural prevention — not 'be careful'). Rate each vector: Critical / High / Medium / Low."`
- Read / check: Verify each attack vector is concretely described (not "someone injects a bad prompt" but "an attacker plants a SYSTEM: override comment in a dependency's README that the agent reads during an npm install"); verify severity is grounded in the specific deployment context (a code-review agent has different blast radius from a deployment agent); verify mitigations are structural (minimal filesystem permissions, human gates on destructive actions) rather than behavioral (trust the agent to recognize attacks); check that the "lethal trifecta" pattern (malicious instruction + capability + off-switch bypass) is addressed as a specific attack class, not just individual injection points.
- Human supplies (Claude can't): **The specific deployment context — filesystem permissions, available tools, credential access — must be supplied by the human.** A generic threat model is less useful than one calibrated to the actual agent's capabilities. The human must know what files and credentials the agent can access. **For production deployments, a security professional's review is required before deployment** — the threat model is a starting point, not a substitute.
- Output medium: Remotion animated threat-register table (vector rows appearing with severity color coding) + screen-recording of injection test.
- The change: add a "defense-in-depth" architecture recommendation — specific technical controls (read-only filesystem mounts, subprocess sandboxing, human-in-the-loop gates before destructive actions) that reduce the exploitability of the Critical and High vectors.
- Teardown angle: The lethal trifecta is not a theoretical threat — it is the predictable consequence of giving an LLM agent write access to a filesystem without architectural constraints. The threat model makes the attack surface explicit before deployment, when the cost of adding controls is low. After an incident, the cost is orders of magnitude higher.
- Exclusions: LLM-specific adversarial training, supply-chain security beyond repository scope, network-level security controls.
- Score: 8/10

## Candidate 08 — Build the Progressive Disclosure Documentation Pattern with Claude
- Source: prompt-engineering-with-clis/chapters/05-progressive-disclosure-and-the-agent-docs-pattern.md
- Lane: BUILD (Claude Code)
- Hook: A CLAUDE.md that inlines your entire architecture is wasting context budget on knowledge the agent doesn't need 90% of the time. Progressive disclosure means the main file is a menu; the details live in linked documents the agent reads only when the task requires them.
- The artifact: a Manim animated architecture diagram showing the progressive disclosure structure — CLAUDE.md (500-word menu) → linked docs (architecture.md, api-conventions.md, testing-guide.md, security-policy.md) → inline code comments — with an animated task flow showing which documents the agent reads for three different task types (bug fix, API extension, security review), and a token-cost comparison for each task.
- Prompt seed: `claude "Design a progressive disclosure documentation architecture for a Python web service repository with 30 engineers. (1) Write a CLAUDE.md under 500 words that serves as the menu: names the linked documents, summarizes when each should be read, and contains only the rules that apply to every session; (2) Write the linked document headers for: architecture.md (high-level design decisions), api-conventions.md (request/response patterns, naming), testing-guide.md (how to write and run tests), security-policy.md (what requires human approval). Each header should describe what the agent learns from reading the document and when it should read it."`
- Read / check: Verify CLAUDE.md is under 500 words and does not inline any document content (only headers and one-sentence summaries per linked document); verify each linked document header accurately describes when the agent should read it (the agent should read architecture.md for structural changes, not for bug fixes); verify the "when to read" guidance is actionable (not "read if relevant" — that requires the agent to already know whether it's relevant); check that the CLAUDE.md explicitly tells the agent to check for linked documents before starting a task.
- Human supplies (Claude can't): The actual content of the linked documents must reflect the real repository's conventions — the human must know their actual architecture decisions, API patterns, and testing approach. **Claude can generate the structure and headers; the human must fill in the accurate content.** The progressive disclosure pattern is most valuable when the linked documents contain genuine, project-specific knowledge.
- Output medium: Manim (animated architecture diagram showing the documentation hierarchy + task-flow animation showing which documents are read per task type + token-cost comparison bars).
- The change: measure the token cost of reading the full CLAUDE.md + all linked documents (total documentation budget) vs. reading only the relevant linked document for each task type — showing that progressive disclosure reduces per-task documentation overhead by 60–80% for tasks that only require one linked document.
- Teardown angle: Static context is always loaded; dynamic context is read on demand. A monolithic CLAUDE.md forces the agent to process 5,000 words of documentation for every task, even if the task only requires 200 words. Progressive disclosure preserves the budget for the information that actually applies to the task at hand — which is almost always a small fraction of the total documentation.
- Exclusions: documentation-as-code tooling, automated documentation generation, knowledge base systems beyond file-based docs.
- Score: 7/10
