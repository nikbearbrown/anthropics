## Candidate 01 — "Build the Benchmark Harness with Claude Code"
- Source: algorithms-vol1/chapters/02-algorithm-analysis.md   LLM Exercise
- Lane: BUILD (Claude Code)
- Hook: You can claim an algorithm is O(n log n) — but without measuring it, you're trusting the analysis, not the implementation. The harness runs the claim against real numbers and shows you whether the code agrees.
- The artifact: a working `harness.py` (~200 lines) that times three demo algorithms (linear scan, binary search, naive matrix multiplication), fits their empirical growth curves against O(1)/O(log n)/O(n)/O(n log n)/O(n²)/O(n³) candidates using log-log regression, and produces annotated growth-curve plots for each — plus a "surprising finding" grounded in actual benchmark output (the crossover where small-n constants dominate before asymptotic class takes over).
- Prompt seed: `claude "Build a reusable benchmark harness in chapters/ch02_algorithm_analysis/harness.py. Export: time_function(fn, input_generator, sizes, repeats=5, warmup=2) returning {size: [t_ns, ...]}; fit_growth_rate(timings) returning best-fit growth class, R^2, and inferred constant; plot_growth(timings, title, out_path, theoretical=None) saving a log-log scatter with reference curve; master_theorem(a, b, f_exponent, log_factor=0) returning case and bound. Then benchmark linear_scan, binary_search, and naive_matmul. Assert fit_growth_rate correctly identifies each. Save plots to figures/. Note any surprising finding from actual output."`
- Read / check: CODE — confirm time_function uses warmup runs and discards them before measurement; confirm log-log regression is implemented correctly (transform both axes, then fit linear). OUTPUT — verify the fit for binary_search reports O(log n) and not O(1) or O(n); confirm the surprising-finding note is drawn from the actual numbers, not invented.
- Human supplies: Nothing — fully synthetic. Claude generates, runs, and benchmarks all three algorithms. No hardware capture needed — the benchmark runs on whatever machine the viewer uses, and the interesting finding (small-n constants vs. large-n growth class) emerges from any modern CPU.
- Output medium: Manim — animated log-log plot with three curves drawing simultaneously: linear scan (O(n)), binary search (O(log n)), naive matmul (O(n³)); reference lines overlay in a second color; the crossover region is annotated live as the curves separate.
- The change: Swap `time_function` to use `time.process_time_ns` instead of `time.perf_counter_ns` and re-run — the viewer watches how the two timing methods diverge under different system loads.
- Teardown angle: An asymptotic bound is a claim about growth, not a measurement — and the claim can be wrong in the regime that matters for your workload. The design lesson: always verify the bound empirically before the bound governs a production decision.
- Exclusions: Profiling memory, GIL effects, SIMD optimizations — stay on timing and growth-class identification.
- Score: 9/10
