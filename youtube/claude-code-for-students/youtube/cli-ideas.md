## Candidate 01 — Build and Audit a Specification Prompt vs. a Vague Request with Claude Code
- Source: claude-code-for-students/chapters/08-prompts-as-specifications.md
- Lane: BUILD (Claude Code)
- Hook: Two prompts, one minute apart, same model — the specification prompt produces forty lines of correct code; the vague one produces eighty lines importing a library that breaks the lab machine.
- The artifact: a side-by-side comparison running two prompts (weak: "help me parse my grades CSV" vs. specification: full five-element prompt from ch.8) through Claude Code, with a diff showing the structural differences in output — animated as two terminal windows filling simultaneously.
- Prompt seed (strong version): `claude "Write parse_grades(path: str) -> list[Grade] in parsers/grades.py. Invariants: standard library only — no pandas; quoted fields containing commas must parse correctly; UTF-8 BOM must be tolerated; empty cells become None not empty string. Context: Grade dataclass defined in models/grade.py; SDD §1.4 specifies the file format. Output: one Python file; then run python -m pytest tests/test_parser.py -q and report exit code. Do not modify models/grade.py. Do not add new dependencies."`
- Read / check: verify the strong prompt output uses csv module (not pandas); verify it opens with encoding="utf-8-sig"; verify empty cells become None; run pytest and confirm exit code 0; verify models/grade.py was not touched.
- Human supplies: models/grade.py with Grade dataclass, tests/test_parser.py with at least three test cases (can be the book's exact example — synthetic).
- Output medium: screen-recording mp4 (split terminal: weak prompt left, specification prompt right; diff highlighted)
- The change: run the weak prompt twice and show the two outputs differ (non-deterministic library choice); run the specification prompt twice and show the outputs are functionally equivalent.
- Teardown angle: a specification is not a longer prompt — it is a different kind of thing; it leaves Claude nothing to guess that wasn't authorized, and the guesses Claude makes on a weak prompt are drawn from training data that doesn't know your project.
- Exclusions: DSPy prompt optimization, full IEEE 830 specification standard, system prompt engineering for production.
- Score: 9/10

## Candidate 02 — Catch a Package Hallucination Before It Becomes a Slopsquatting Attack with Claude Code
- Source: claude-code-for-students/chapters/05-five-supervisory-capacities.md
- Lane: BUILD (Claude Code)
- Hook: Claude imports `requests_oauth_helper` — a name that doesn't exist on PyPI today but might be squatted tomorrow with malicious code inside.
- The artifact: a Python scanner that reads Claude-generated import statements from a file, checks each package name against the PyPI JSON API, and flags any that return 404 as "hallucinated / slopsquatting risk" — animated as import lines being scanned with red/green verdicts appearing.
- Prompt seed: `claude "Write package_auditor.py: reads a Python file, extracts all import statements (import X and from X import Y), queries PyPI's JSON API (https://pypi.org/pypi/{package}/json) for each package, and reports: EXISTS / HALLUCINATED. Flag any 404 as a potential slopsquatting risk. Run it on the attached generated file."`
- Read / check: verify the scanner correctly identifies a real package (requests → EXISTS); verify it catches a fabricated name (requests_oauth_helper → HALLUCINATED); verify the PyPI API call uses only the top-level package name (not submodules); test on a file containing at least one real and one fake import.
- Human supplies: a Claude-generated Python file containing at least one hallucinated import (trivially generated by asking Claude for a niche utility — synthetic).
- Output medium: screen-recording mp4 (terminal: scanner running, real imports green, hallucinated import red, slopsquatting risk warning printed)
- The change: add a --npm flag that checks npm's registry API for JavaScript imports using the same pattern.
- Teardown angle: the hallucination rate is low but the recurrence rate is high — slopsquatting works because the same fake package names appear across thousands of model outputs; the scanner catches the risk at the import line before `pip install` runs.
- Exclusions: supply-chain attack deep-dive, full Spracklen 2024 replication, npm audit tooling.
- Score: 9/10

## Candidate 03 — Write a Five-Artifact Software Design Document with Claude Code
- Source: claude-code-for-students/chapters/07-software-design-document.md
- Lane: BUILD (Claude Code)
- Hook: Three hours of drift because "a local-only editor" became a multi-user backend — one eleven-minute SDD prevents it.
- The artifact: a Claude-assisted SDD generation pipeline that takes a v0 sentence (one sentence, one user, one outcome), runs the Principle Collision Test on three architecture principles, and outputs a complete five-section SDD — animated as the five sections building in dependency order.
- Prompt seed: `claude "Given this v0: 'A local-only timeline editor for one Midnight Fuel developer to lay out today's light-flicker cues, mark each ready, and copy the Luau table, without a login.' Generate a five-section SDD: (1) Problem Statement (refine v0 to name user + done-condition), (2) Architecture Principles (3 principles, each passable through the Principle Collision Test), (3) Core User Flows (the one essential path), (4) User Needs (3 testable conditions), (5) Component List (specific names + explicit non-components). Run the Principle Collision Test on the three principles and report."`
- Read / check: verify the Problem Statement names a single user and a done-condition; verify each Architecture Principle passes the Collision Test (two principles conflict under at least one realistic scenario); verify each User Need is testable (stopwatch-and-laptop measurable); verify the Component List names at least one explicit non-component ("no backend").
- Human supplies: a v0 sentence for any simple local tool (the book's flicker-cue editor is the worked example — synthetic).
- Output medium: screen-recording mp4 (terminal: v0 input, five-section SDD generated, Collision Test results printed)
- The change: take the first SDD and add "multi-user sync" to the scope — verify the Architecture Principles conflict is immediate and visible (local-only vs. sync) and Claude flags the conflict rather than silently resolving it.
- Teardown angle: the SDD is the decision that prevents you from making the same decision twice under deadline pressure — and the Principle Collision Test is what separates a real principle from a tagline.
- Exclusions: IEEE 1016 full standard, ADR tooling, arc42 template walkthrough.
- Score: 9/10

## Candidate 04 — Score a Build Using the Boondoggle Score with Claude Code
- Source: claude-code-for-students/chapters/11-planning-first-build.md
- Lane: BUILD (Claude Code)
- Hook: Before Claude sees a single prompt, you know which step is highest-risk, which handoff condition is weakest, and which supervisory capacity you're most likely to skip.
- The artifact: a Python Boondoggle Score generator that takes a list of build steps (phase, labor=Claude/human, supervisory capacity, handoff condition) and prints a scored table with: critical path identified, highest-risk handoff flagged, supervisory capacity distribution checked — animated as the table filling in with a critical-path highlight.
- Prompt seed: `claude "Generate a Boondoggle Score table for Phase 1 of an application tracker (add, mark submitted, delete applications). Columns: step#, phase, labor (Claude/human), supervisory capacity (for human steps), handoff condition (machine-checkable). Include at least 5 steps. Flag the critical path and identify the highest-risk handoff. Every handoff condition must name a specific test file, count, or artifact — not 'Claude finishes.'"`
- Read / check: verify every handoff condition is machine-checkable (names a file, a count, or a test pass); verify the critical-path arrow connects sequential dependencies correctly; verify at least one human step names a supervisory capacity from the five (PA, PF, TO, IJ, EI); flag any human row that says "domain knowledge" in every capacity column.
- Human supplies: nothing — the application tracker from ch.11 is the worked example — synthetic.
- Output medium: Manim (table animating row by row, critical path highlighted with an arrow, highest-risk row bordered in red)
- The change: deliberately set row 1's handoff condition to "Claude completes the data model" — verify the scorer flags it as invalid (not machine-checkable) and requests a revision.
- Teardown angle: the Score is a diagnostic before a single line of code is written — it tells you where the build will fail before it has a chance to; the highest-risk row is always the one that every other row inherits from.
- Exclusions: full Boondoggling framework introduction, formal software project management methodologies.
- Score: 9/10

## Candidate 05 — Run the Three-Pass Verification Protocol with Claude Code
- Source: claude-code-for-students/chapters/13-verification.md
- Lane: BUILD (Claude Code)
- Hook: The test suite passes — and the user can't see their most important data at a glance. Pass 3 catches what Pass 1 and Pass 2 miss.
- The artifact: a three-pass verification report generated after a Claude Code build session: Pass 1 (functional: does it run on the happy path?), Pass 2 (edge-case: does it handle empty/malformed/boundary inputs?), Pass 3 (SDD needs: does it satisfy the user needs section, read aloud, by a person who didn't build it?) — animated as three labeled passes with pass/fail/loop-back verdicts.
- Prompt seed: `claude "Run the three-pass verification protocol on this application tracker build: Pass 1: run the happy path (add 3 apps, toggle 2 submitted, refresh, confirm state preserved). Pass 2: test boundary inputs (0 apps, duplicate school name, very long string in school field, corrupted localStorage). Pass 3: read the SDD user needs aloud and tell me whether the build satisfies each one as it currently runs. Flag any Pass 3 failure as a 'needs vs. tests gap.'"`
- Read / check: verify Pass 1 produces a functional verdict (not just "tests passed"); verify Pass 2 names specific boundary inputs and their outcomes; verify Pass 3 reads the SDD User Needs literally (not the test descriptions) and flags the ch.13 "at a glance" need as a failure; confirm the loop-back is recommended when Pass 3 fails.
- Human supplies: a running application tracker build from Phase 1 (the book's worked example, synthetic) and its SDD with User Needs section.
- Output medium: screen-recording mp4 (terminal: three passes run sequentially, Pass 3 failure highlighted, loop-back to Pass 1 shown)
- The change: amend the SDD to remove the "at a glance" user need and re-run Pass 3 — verify it now passes, demonstrating that "done" is always relative to the spec, not absolute.
- Teardown angle: tests verify code against tests — only a human reading the SDD user needs aloud can catch the gap between what was built and what was needed; Pass 3 is the pass the test runner cannot run.
- Exclusions: mutation testing full walkthrough, Defects4J benchmark replication, ISO 25010 full compliance.
- Score: 9/10

## Candidate 06 — Demonstrate the Solve-Verify Asymmetry with Claude Code
- Source: claude-code-for-students/chapters/02-division-of-labor.md
- Lane: BUILD (Claude Code)
- Hook: Claude's solve speed doubles every eighteen months. Your verification speed is approximately constant. The gap is widening — and the only defense is to get better at the verify side.
- The artifact: a timed comparison: Claude solves a sorting function in 8 seconds; a human verifies it (adds a tie-breaking test case, runs it, finds the bug) in 4 minutes — the ratio visualized as an animated line chart with two diverging trends.
- Prompt seed: `claude "Write a Python function top_three_by_gpa(students: list[dict]) -> list[dict] that returns the top three students by GPA, breaking ties alphabetically by last name. Students have keys 'name', 'last_name', 'gpa'."`
- Read / check: verify the function contains the tie-breaking bug (sort by last_name ascending but not correctly in a stable sort — the ch.2 Bell/Adams bug); verify the bug is invisible on a test set with no ties; verify it appears when a tie case is added; time both the generation (Claude) and the plausibility audit + fix (human).
- Human supplies: a test set with three students and no ties (the bug is invisible until the human adds a tie case — the bug is present in the expected Claude output).
- Output medium: Manim (timeline animation: Claude generate = 8s bar, human verify = 4min bar, plus a line chart showing solve speed rising vs. verify speed flat over time)
- The change: ask Claude to audit its own function for tie-breaking correctness — verify it reports "looks correct" without catching the bug, confirming that self-check shares the production failure mode.
- Teardown angle: your job is not to solve faster — Claude has that side; your job is to verify better; if you compete on solve speed you lose, and you should; if you abandon verify, the build ships with whatever Claude got wrong.
- Exclusions: formal algorithmic complexity analysis, full Kahneman System 1/2 literature review.
- Score: 9/10

## Candidate 08 — Build and Test a Handoff Condition Protocol with Claude Code
- Source: claude-code-for-students/chapters/09-handoff-conditions-dangerous-middle.md
- Lane: BUILD (Claude Code)
- Hook: "Claude is done" is not a handoff condition — a handoff condition names the test file, the case count, and the inputs that must pass before the next step begins.
- The artifact: a Python build-step validator that reads a Boondoggle Score JSON (steps with handoff_conditions), runs each handoff condition as a shell command or pytest filter, and prints a pass/fail per step — animated as steps lighting up green as their conditions pass.
- Prompt seed: `claude "Write handoff_validator.py: reads boondoggle_score.json (list of steps with 'handoff_condition' as a shell command string), runs each command via subprocess, and reports: step number, condition, exit code, PASS/FAIL. Stop on first FAIL and report which step blocked."`
- Read / check: verify the script runs the test commands via subprocess (not as Claude self-evaluation); verify FAIL stops the chain and names the blocking step; verify PASS correctly requires exit code 0 from a real test runner; test with three steps where step 2 fails.
- Human supplies: a boondoggle_score.json with at least three steps and one deliberately failing handoff condition (synthetic — the application tracker example works).
- Output medium: screen-recording mp4 (terminal: three steps run, step 2 fails, chain stops, blocking step named)
- The change: make all three steps pass and verify the validator prints a clean success report and names the next phase gate.
- Teardown angle: a handoff condition is machine-checkable or it is not a handoff condition — the validator enforces this mechanically; the dangerous middle exists precisely where "Claude thinks it's done" is confused with "the condition passed."
- Exclusions: CI/CD pipeline integration, GitHub Actions handoff automation.
- Score: 8/10
