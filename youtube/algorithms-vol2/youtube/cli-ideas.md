## Candidate 01 — "Research Your Own Decision with Claude: Bayesian Edition"
- Source: algorithms-vol2/chapters/01-bayes-rule-and-bayesian-inference.md   LLM Exercise
- Lane: RESEARCH (Claude assistant)
- Hook: The test is 99% accurate and the result is positive — and the patient is still 91% likely to be fine. The base rate matters more than the test, and almost nobody runs the arithmetic before making the consequential decision.
- The artifact: a structured Bayesian decision diary entry — for one real decision the viewer is currently facing, a completed 8-section document: The decision, Prior (with a probability estimate, not just a direction), Likelihood, Posterior (worked arithmetic), Base-rate check, What I'll do next, What would change my mind, Outcome (to fill in later). The entry is designed to survive a re-read six months later when the outcome is known.
- Prompt seed: `claude "Help me work through this decision as a Bayesian inference problem. The decision: [name it]. Step 1: State my prior as a probability, and push back if my prior feels like post-hoc rationalization. Step 2: Name the likelihood — P(evidence | hypothesis) and P(evidence | NOT hypothesis). Step 3: Compute the posterior. Step 4: Force me to check the base rate for this type of decision. Step 5: Name the misconception I'm at risk of (Bayesian methods require a strong prior — I always have one). Output: an 8-section diary entry with headings: The decision / Prior / Likelihood / Posterior / Base-rate check / What I'll do next / What would change my mind / Outcome (to fill in later)."`
- Read / check: Verify the prior is stated as a number (not "I'm leaning toward yes"). Check that Claude runs the posterior arithmetic explicitly — not just estimates. Verify the base-rate check references a real comparison class. Confirm the "What would change my mind" section names specific, observable evidence.
- Human supplies: A real decision the viewer is currently facing — this is the non-negotiable human input. Claude cannot supply the decision or the viewer's actual prior beliefs. The diary entry is meaningless without the viewer's lived context. "Nothing" is not acceptable here; the whole exercise is applying the method to the viewer's actual situation.
- Output medium: Manim — a Bayes tree diagram animates: prior probability splits into two branches (H / ¬H), each branch produces a likelihood, totals combine into the marginal, posterior is computed and highlighted; the arithmetic appears at each node as the tree grows.
- The change: Add a second round of evidence (a new data point that arrives after the initial analysis) and update the posterior again — the viewer watches a sequential Bayesian update in real time.
- Teardown angle: The inverse fallacy confuses P(evidence | hypothesis) with P(hypothesis | evidence) — and the difference can be the difference between 99% and 9%. The design lesson: always write down which conditional probability you actually know before computing the one you want.
- Exclusions: Bayesian networks, MCMC, hierarchical models — this is the single-decision, single-update case.
- Score: 9/10

## Candidate 02 — "Build the Optimal Stopping Simulator with Claude Code"
- Source: algorithms-vol2/chapters/02-optimal-stopping.md
- Lane: BUILD (Claude Code)
- Hook: The 37% rule says: observe the first 37% of candidates without hiring, then take the next one who is better than everyone you've seen. Simulate it across 10,000 hiring runs and watch the success rate converge to 1/e — the math becomes a number.
- The artifact: a complete optimal stopping simulator — the classical secretary problem with configurable n (number of candidates), the 37% threshold strategy vs. brute-force search over all threshold values, 10,000 simulation runs per threshold value, a plot of success probability vs. threshold value (with the peak at n/e annotated), and an extension to the "sultan's dowry" variant (candidates have real-valued quality scores, not just relative rankings).
- Prompt seed: `claude "Simulate the secretary problem (optimal stopping). Parameters: n candidates, random permutation of quality scores. Implement: observe_and_reject_phase(candidates, m) that records the max quality seen in first m candidates without accepting. stopping_strategy(candidates, m, threshold) that returns the first candidate in positions m+1..n who beats the threshold (or the last candidate). Run 10000 simulations per threshold value m in [1..n-1] for n=100. Plot success_rate vs m/n. Mark the theoretical optimum at m = n/e ≈ 37%. Extension: repeat with real-valued Gaussian quality scores (not just rank) and report whether the optimal threshold shifts."`
- Read / check: CODE — confirm the simulation correctly returns the last candidate if no one beats the threshold (not None or a failure state). OUTPUT — success rate at threshold m = floor(n/e) should be close to 1/e ≈ 0.368 (within ±0.01 across 10000 runs); the success-rate curve should peak near m/n = 0.37 and decline on both sides; the Gaussian extension should show the same threshold behavior.
- Human supplies: Nothing — fully synthetic. The quality scores are randomly generated; the simulation is entirely self-contained.
- Output medium: Manim — animated plot builds left to right as threshold values sweep from 1 to n-1; the success-rate curve traces itself out; a vertical line marks n/e; the curve peaks at the line; a label "1/e ≈ 36.8%" marks the peak; final annotation shows how much worse "interview everyone then pick" performs.
- The change: Add a variant where the interviewer can "call back" a previously seen candidate with probability p — and find the new optimal stopping point. The viewer watches the strategy change as callback probability increases from 0 to 1.
- Teardown angle: 37% is not an approximation — it is the exact optimal threshold in the limit. The design lesson: the optimal stopping rule is deterministic because you've already committed to a strategy before you see any candidates; the strategy sets the threshold, the threshold governs the decision.
- Exclusions: Optimal stopping under discounting, Pandora's box problem, multi-dimensional candidate assessment.
- Score: 9/10

## Candidate 03 — "Build the Multi-Armed Bandit Simulator with Claude Code"
- Source: algorithms-vol2/chapters/03-explore-vs-exploit-multiarmed-bandits.md   LLM Exercise
- Lane: BUILD (Claude Code)
- Hook: Epsilon-greedy, UCB, and Thompson sampling all solve the same explore/exploit problem — but they have different regret curves, and Thompson sampling's Bayesian update produces the lowest regret on stationary arms in almost every benchmark. Simulate 10,000 rounds and see which one wins.
- The artifact: three bandit algorithms (epsilon-greedy with configurable epsilon, UCB1 with configurable confidence width, Thompson sampling with Beta-Bernoulli conjugate), a 10,000-round simulation across a 5-arm bandit with known Bernoulli reward probabilities, cumulative regret curves for all three strategies, and a stationarity-violation test where arm means shift midway through the simulation.
- Prompt seed: `claude "Simulate a 5-arm Bernoulli bandit with arms having reward probabilities [0.1, 0.3, 0.5, 0.7, 0.9]. Implement: epsilon_greedy(epsilon, n_rounds) — with probability epsilon explore random arm, else exploit; ucb1(n_rounds) — select arm with highest empirical mean + sqrt(2 log t / n_i); thompson_sampling(n_rounds) — maintain Beta(alpha_i, beta_i) for each arm, sample, select max. Run 10000 rounds per strategy, compute cumulative regret (optimal arm reward - selected arm reward at each step). Plot cumulative regret curves. Stationarity test: at round 5000, swap arm means to [0.9, 0.7, 0.5, 0.3, 0.1] and re-run."`
- Read / check: CODE — confirm Thompson sampling updates Beta parameters correctly (alpha_i += reward, beta_i += 1 - reward). OUTPUT — Thompson sampling should have the lowest total regret on the stationary arms; epsilon-greedy should adapt faster than UCB when means shift (it explores by probability, not confidence bound); all three strategies should eventually identify the best arm on stationary inputs.
- Human supplies: Nothing — fully synthetic. Bernoulli arm probabilities are configured in the prompt.
- Output medium: Manim — three cumulative regret curves draw simultaneously in different colors (epsilon-greedy, UCB1, Thompson); at round 5000 the stationarity violation is marked by a vertical dashed line; the curves diverge after the shift; final annotation shows total regret per strategy.
- The change: Add a contextual bandit variant where the optimal arm depends on a feature (morning vs. evening) — the viewer watches Thompson sampling adapt to context faster than UCB.
- Teardown angle: A/B testing is a two-arm bandit run for a fixed duration — which means you commit to the exploration budget before seeing the data. The design lesson: choose the bandit strategy based on your trial budget, reward signal noise, and whether the environment is stationary.
- Exclusions: Lin-UCB (linear contextual bandits), Gaussian process bandits, bayesian optimization — those require a different reel.
- Score: 9/10

## Candidate 04 — "Build the Game Theory Simulator with Claude Code"
- Source: algorithms-vol2/chapters/04-game-theory.md   LLM Exercise
- Lane: BUILD (Claude Code)
- Hook: Nash equilibrium is not the best outcome — it's the stable one. The Prisoner's Dilemma has a Nash equilibrium at mutual defection, which is worse for both players than mutual cooperation. Build the simulator and watch rational agents make each other worse off.
- The artifact: a game theory simulator supporting 2×2 normal-form games — Prisoner's Dilemma, Stag Hunt, Chicken, Battle of the Sexes — with Nash equilibrium finder (pure and mixed), iterated elimination of dominated strategies, and an iterated Prisoner's Dilemma with configurable strategies (always cooperate, always defect, tit-for-tat, Pavlov/win-stay-lose-shift) run for 200 rounds with payoff history plots.
- Prompt seed: `claude "Build a 2×2 game theory simulator. Support: Prisoner's Dilemma (T=5,R=3,P=1,S=0), Stag Hunt, Chicken, Battle of the Sexes. Implement: find_pure_nash(payoff_matrix_A, payoff_matrix_B) returning all pure Nash equilibria; find_mixed_nash(payoff_A, payoff_B) for 2×2 games; iterated_elimination_dominated(payoff_A, payoff_B). Iterated PD: strategies = always_cooperate, always_defect, tit_for_tat, pavlov (win-stay-lose-shift). Run all pairs of strategies for 200 rounds. Plot cumulative payoff histories. Report the tournament ranking."`
- Read / check: CODE — confirm Nash equilibrium finder checks both players' best responses (not just one), confirm mixed Nash uses the indifference condition correctly. OUTPUT — Prisoner's Dilemma must find (Defect, Defect) as the unique pure Nash and no other; tit-for-tat should achieve near-optimal payoff against itself and most strategies in the iterated tournament; always-defect should do well short-term and poorly in the long tournament.
- Human supplies: Nothing — fully synthetic.
- Output medium: Manim — the iterated PD tournament: a round-robin matrix builds showing each strategy pair's cumulative payoff; cells fill in one by one; final frame shows the tournament ranking as a sorted bar chart, tit-for-tat near the top.
- The change: Add a noisy version of tit-for-tat (with 5% defection probability on cooperation rounds) and re-run the tournament — the viewer watches how noise changes cooperation stability.
- Teardown angle: Nash equilibrium is a fixed point, not a recommendation. The design lesson: identifying the equilibrium tells you where rational agents will land; it does not tell you whether that landing point is good. The design problem is the payoff matrix, not the strategy.
- Exclusions: Extensive-form games, mechanism design, auction theory — those require a different reel.
- Score: 8/10

## Candidate 05 — "Build the Scheduling Optimizer with Claude Code"
- Source: algorithms-vol2/chapters/05-scheduling.md
- Lane: BUILD (Claude Code)
- Hook: Sorting by priority is exactly right for one specific scheduling problem — and wrong for almost every other one. Build SJF, EDF, and the weighted job-scheduling DP, and watch "sort by priority" fail on a carefully constructed counterexample.
- The artifact: three scheduling algorithms (Shortest Job First for minimum total completion time, Earliest Deadline First for minimum maximum lateness, weighted job scheduling DP for maximum profit under deadline constraints), correctness-verified via exchange argument adversarial inputs for SJF alternatives, and an empirical counterexample generator that shows "sort by priority" failing while EDF succeeds on the same instance.
- Prompt seed: `claude "In a scheduling module: implement sjf(jobs) sorting by processing time for minimum total completion time, edf_preemptive(jobs, deadlines) for minimum maximum lateness (preemptive), weighted_job_scheduling_dp(jobs, weights, deadlines) for maximum weight before deadlines (DP on sorted finish times). Generate adversarial inputs where 'sort by priority' (sort by urgency score = weight/processing_time) fails to minimize total completion time but SJF succeeds. Report average and worst-case suboptimality of priority-sort vs SJF on 1000 random inputs."`
- Read / check: CODE — SJF must sort by processing time (not by priority or value), EDF must use preemption (not just ordering), weighted DP must return both the optimal weight and the selected job set. OUTPUT — adversarial generator must produce instances where priority-sort is clearly suboptimal (ratio > 1.1 on average); EDF must succeed on all instances where a feasible schedule exists; DP optimal must match brute-force on small instances (n ≤ 8).
- Human supplies: Nothing — fully synthetic.
- Output medium: Manim — two Gantt charts animate side by side for the same job set: "sort by priority" on the left (red completion times), SJF on the right (green completion times); total completion time labels appear below each; the gap is annotated.
- The change: Add a multi-machine extension — parallel machines with identical speed — and find the optimal job assignment using list scheduling (LPT rule). Report the approximation ratio vs. optimal.
- Teardown angle: The scheduling objective determines the optimal algorithm — and the objectives are not interchangeable. The design lesson: before choosing a scheduling policy, write down the objective function. SJF minimizes average wait. EDF minimizes maximum lateness. They are different problems.
- Exclusions: Job shop scheduling (NP-hard), preemption on multiple machines, online scheduling with unknown jobs.
- Score: 8/10

## Candidate 06 — "Build the Gale-Shapley Stable Matching Simulator with Claude Code"
- Source: algorithms-vol2/chapters/06-stable-matching-and-galeshapley.md   LLM Exercise
- Lane: BUILD (Claude Code)
- Hook: Stable matching is not fair — the proposer side gets its best stable outcome and the receiver side gets its worst. The same algorithm, with the sides swapped, produces a completely different matching. Build it and show the difference.
- The artifact: the Gale-Shapley deferred acceptance algorithm in both proposer-optimal and receiver-optimal forms, a stability verifier (checks that no two unmatched pairs both prefer each other over their current match), a worst-case example where proposer-optimal and receiver-optimal matchings differ on all matched pairs, and an unraveling demonstration showing what happens when side deals (early commitments) create instability.
- Prompt seed: `claude "Implement gale_shapley_proposer_optimal(proposers, receivers, proposer_prefs, receiver_prefs) and gale_shapley_receiver_optimal using deferred acceptance. Implement is_stable_matching(matching, proposer_prefs, receiver_prefs) that returns True iff no blocking pair exists. Generate a 5×5 preference matrix where proposer-optimal and receiver-optimal matchings differ on all 5 pairs. Unraveling demo: simulate early-commitment instability — a receiver accepts a proposer's early offer before seeing later higher-ranked proposers. Show the resulting blocking pairs."`
- Read / check: CODE — confirm the stability verifier checks all n² pairs (not just adjacent pairs). OUTPUT — the 5×5 counterexample must produce different matchings on all 5 pairs (not just some); the unraveling demo must produce at least one blocking pair after early commitment; proposer-optimal must match the expected result on the classic example (men/women or students/schools with known preference lists).
- Human supplies: Nothing — fully synthetic. The 5×5 counterexample is a known construction that can be generated programmatically.
- Output medium: Manim — animated bipartite matching: proposers on the left, receivers on the right; proposal arrows animate as the algorithm runs; deferred acceptances appear as tentative links; rejections retract; final stable matching highlighted in green. A second frame shows the receiver-optimal matching with different links highlighted.
- The change: Run the algorithm on a real medical residency match scenario (provide a 6-student × 6-hospital preference matrix) and show which side benefits from the proposer/receiver assignment.
- Teardown angle: Stable matching is strategy-proof for the proposing side — they should submit true preferences — but not for the receiving side in many-to-one cases. The design lesson: who proposes determines who benefits. Build the algorithm for the side that should be strategy-proof.
- Exclusions: Many-to-many matching, capacitated matching extensions, matching markets with money.
- Score: 8/10

## Candidate 07 — "Build the Randomized Networking Simulator with Claude Code"
- Source: algorithms-vol2/chapters/07-randomness-and-networking.md   LLM Exercise
- Lane: BUILD (Claude Code)
- Hook: Random load balancing outperforms shortest-queue routing under adversarial traffic — not because it's lucky, but because it breaks the correlation that deterministic routing exploits. The power-of-two-choices result shows the gap.
- The artifact: three load balancing strategies (round-robin, join-shortest-queue, power-of-two-choices — pick the best of 2 random servers), a gossip protocol simulation (epidemic broadcast on a 100-node network, measuring rounds to full coverage), and a consistent hashing simulator with configurable virtual node count (measuring load imbalance as node count varies).
- Prompt seed: `claude "Load balancing simulator: implement round_robin, join_shortest_queue, power_of_two_choices (pick best of 2 random servers) for a fleet of 10 servers with Poisson(lambda=0.8/server) arrivals and Exp(1.0) service times. Run 10000 requests, plot maximum queue length over time for each policy, report mean and max load imbalance. Gossip simulator: 100 nodes, one node starts with message, each round each infected node contacts 3 random others. Plot fraction infected vs rounds, report rounds to 99% coverage. Consistent hashing: vary virtual nodes from 10 to 500, plot load imbalance (max/min keys per node)."`
- Read / check: CODE — power-of-two-choices must sample 2 servers uniformly at random (not the two most loaded), gossip must use push gossip (infected nodes initiate contact). OUTPUT — power-of-two-choices should produce significantly lower max queue length than round-robin under adversarial traffic; gossip should reach 99% coverage in O(log n) rounds (approximately 7 rounds for 100 nodes); consistent hashing imbalance should decrease sharply as virtual nodes increase past ~100.
- Human supplies: Nothing — fully synthetic.
- Output medium: Manim — three animated queue-length traces (round-robin, join-shortest, power-of-two) draw simultaneously; power-of-two stays lowest; a running max-load counter tracks each strategy; final frame shows the gap as a bar chart.
- The change: Make the traffic adversarial (send all requests to the same server hash key range) and compare the three strategies — the viewer sees which ones are robust to targeted attacks.
- Teardown angle: Randomization breaks the correlation that adversarial traffic exploits. The design lesson: the power-of-two-choices result is a 1988 theorem that every cloud load balancer has re-discovered — the theory predicts practice within a constant factor.
- Exclusions: TCP congestion control, BGP routing, distributed consensus protocols.
- Score: 8/10

## Candidate 08 — "Build the Social Network Analysis Suite with Claude Code"
- Source: algorithms-vol2/chapters/08-social-networks.md
- Lane: BUILD (Claude Code)
- Hook: The most important person in any network is almost never who you think — degree centrality picks the most-connected node, but betweenness centrality picks the bridge, and removing the bridge disconnects the network while removing the hub barely dents it.
- The artifact: four centrality measures (degree, eigenvector, betweenness, PageRank), a community detection algorithm (Louvain modularity maximization or Girvan-Newman edge betweenness), an influence maximization greedy algorithm (submodular greedy with lazy evaluation for k=5 seed nodes), and a weak-ties demonstration on a synthetic network — showing that removing weak-tie bridges disconnects the network while removing hub nodes does not.
- Prompt seed: `claude "Social network analysis suite. Implement: degree_centrality(G), eigenvector_centrality(G) via power iteration (20 iterations), betweenness_centrality(G) exact O(VE), pagerank(G, d=0.85, iterations=50). Community detection: girvan_newman(G) via iterative edge removal on highest-betweenness edge. Influence maximization: greedy_influence_maximization(G, k=5, num_simulations=100) using independent cascade model. Weak ties demo: generate a graph with 3 dense clusters + 2 bridge edges. Show that removing bridge edges disconnects clusters; removing 2 hub nodes (highest degree) does not disconnect."`
- Read / check: CODE — PageRank must include the teleportation factor (with probability 1-d jump to uniform random node), betweenness centrality must count shortest paths correctly (using BFS for unweighted graphs). OUTPUT — betweenness centrality must identify the bridge nodes as highest-betweenness in the weak-ties demo (not the hub nodes); PageRank should converge within 50 iterations for typical graphs; Girvan-Newman should correctly separate the 3 clusters in the demo graph.
- Human supplies: Nothing — fully synthetic. A karate club graph or LFR benchmark graph can be generated programmatically. If the viewer wants a real social network (Twitter ego graph, academic collaboration network), they supply the edge list — but the algorithms run on synthetic by default.
- Output medium: Manim — the weak-ties demo: a graph with 3 dense clusters and 2 thin bridge edges animates; bridge edges are highlighted; first removal severs the network; the graph fragments; then it reconstructs and the two highest-degree hub nodes are removed instead — the network stays connected. Centrality scores animate as node sizes.
- The change: Apply influence maximization to find the optimal 5-seed campaign in a 200-node network and compare the greedy seeds to the 5 highest-degree nodes — the viewer sees that degree centrality is a poor proxy for influence.
- Teardown angle: Centrality is not one thing — it is a question. The question determines the measure. The design lesson: choosing the wrong centrality measure picks the wrong person for the wrong reason.
- Exclusions: Temporal networks, signed networks, hypergraphs, real social media data scraping.
- Score: 8/10
