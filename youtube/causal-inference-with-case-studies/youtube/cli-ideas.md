## Candidate 01 — "Build a Regime-Aware Anomaly Detector with Claude Code: Don't Trust the Sensors"
- Source: causal-inference-with-case-studies/chapters/15-case-confounding-cmapss-turbofan.md
- Lane: BUILD (Claude Code)
- Hook: A turbofan engine running at altitude reads hotter than at sea level. A naive detector fires an alarm. An engineer drowning in 275 alarms in eleven minutes — the Texaco Milford Haven story — learns to ignore them all. The fix is not a better threshold. It's a causal one.
- The artifact: a Python script (~45 lines) that loads the NASA CMAPSS FD002 dataset (public), trains a KMeans regime classifier (k=6) on the three operating-setting columns, fits per-regime linear regressions for five sensor channels (3, 4, 9, 11, 15), computes causal residual z-scores (observed minus regime-conditional expected, normalized by residual std), detects anomaly as mean of top-3 z-scores exceeding threshold, and outputs a Manim animated comparison: global z-score alert rate (100%) vs. regime-conditional alert rate (~66%) on the multi-condition dataset — with false-positive collapse annotated.
- Prompt seed: `claude "Build a Python anomaly detector for NASA CMAPSS FD002 data using back-door adjustment via regime stratification. Steps: (1) load FD002 train/test CSVs; (2) fit KMeans(k=6) on op_setting_1, op_setting_2, op_setting_3; (3) for each regime cluster and each of sensors 3, 4, 9, 11, 15, fit a LinearRegression predicting sensor from op_settings; (4) compute causal z-score = (observed - predicted) / residual_std per sensor; (5) anomaly score = mean of top-3 causal z-scores; (6) flag engines where any window of 20 consecutive cycles exceeds threshold 2.5; (7) compare coverage and F1 vs. a global z-score baseline (means from all data). Print comparison table."`
- Read / check: CODE: verify KMeans k=6 is appropriate (chapter reports silhouette=0.997 confirming six discrete operating points); verify the global baseline produces ~100% alert rate on FD002 (all engines flagged, F1=0.000); verify regime-conditioning drops false positives substantially. OUTPUT: the comparison table should show the regime-aware approach with F1 > 0 vs. F1 = 0 for global baseline — confirming the core causal claim.
- Human supplies: The NASA CMAPSS dataset (free public download from NASA Prognostics Center of Excellence). Claude cannot access external URLs, so the human downloads the four CSV files and specifies the local path. The script is fully reproducible once the data is on disk.
- Output medium: Manim (two animated bar charts side by side: "Global Baseline" bar at 100% alert rate in red labeled "100% false positives, useless"; "Regime-Aware" bar at ~66% in blue labeled "Alert rate after causal adjustment"; F1 score animating in for each; annotation: "The causal fix: condition on what the engine is doing")
- The change: Run the same regime-aware approach on FD001 (single operating condition) and FD002 (six operating conditions) and display both sets of results — demonstrating that regime conditioning is redundant for FD001 (only one regime exists) but essential for FD002 (six regimes confound the sensor readings).
- Teardown angle: The operating settings are the textbook back-door confounder: they cause both the sensor readings and the regime the detector uses to score those readings. Conditioning on regime blocks the back-door path through operating settings and isolates the signal from engine health. The gain is not a better classifier — it's getting off a 100% false-positive rate.
- Exclusions: Structural veto (isentropic coupling test beyond one sentence); remaining useful life regression; alternative anomaly detection methods (Isolation Forest, OCSVM).
- Score: 10/10

## Candidate 02 — "Build a Counterfactual Confound Tester with Claude Code: Is Your Model Tracking Seasonality or Stress?"
- Source: causal-inference-with-case-studies/chapters/20-case-counterfactuals-supply-chain.md
- Lane: BUILD (Claude Code)
- Hook: A supply chain model flags October as high-risk every year. But October is also peak demand month. Is the model detecting genuine operational stress — or is it just reading the calendar?
- The artifact: a Python script (~40 lines) that: (1) generates 730 days of synthetic supply chain data with seasonal patterns (month/quarter effects) and injected disruption events (~4% of days), (2) trains a calibrated logistic regression disruption predictor, (3) runs the counterfactual confound test — refit and score the model on a feature set with month, quarter, and seasonal encodings ablated, (4) counts how many high-confidence predictions (≥80%) survive vs. collapse under ablation, and (5) produces a Manim animated before/after showing high-confidence predictions dissolving when seasonality is removed.
- Prompt seed: `claude "Build a Python counterfactual confound test for a supply chain disruption model. Steps: (1) generate 730 days of synthetic data with features: month, quarter, 7-day rolling averages of delay/inventory/lead_time/demand/transport_stress/weather_risk/supplier_reliability; inject disruption events on ~4% of days by amplifying risk features; (2) train an isotonic-calibrated LogisticRegression; (3) run a baseline prediction pass; (4) re-fit and re-score with month, quarter, and seasonal encodings dropped (ablation); (5) report: how many predictions ≥80% in baseline survive vs. collapse under ablation; (6) generate a Manim scene showing high-confidence predictions appearing and then dissolving when seasonal features are removed."`
- Read / check: CODE: verify the ablation correctly removes month, quarter, and any explicit time-of-year encodings while keeping rolling averages (which carry residual seasonal signal — the chapter acknowledges this limit); verify the calibration step uses isotonic regression correctly. OUTPUT: predictions that survive ablation represent operational-stress signal; those that collapse were seasonal confounds — the script should show a non-trivial fraction of predictions collapsing (confirming the seasonal confound problem).
- Human supplies: Nothing — fully synthetic. The script generates its own data with controlled seasonal confounding. The human optionally supplies real logistics records for a more authentic test, but the synthetic version illustrates the mechanism cleanly.
- Output medium: Manim (animated timeline: day markers scrolling left-to-right; high-confidence prediction flags appearing as red markers; then the "ablation" effect applied — red markers that were seasonally confounded dissolving one by one, leaving only operationally-grounded predictions; counter showing surviving vs. dissolved predictions)
- The change: Add a "partial ablation" test — remove only month (not quarter, not rolling averages) and show how much seasonal confounding persists through correlated features. This illustrates the chapter's key limitation: feature-level ablation is a lower bound on seasonality dependence, not a complete test.
- Teardown angle: The counterfactual question here is not "what is the effect of seasonality on disruption risk" — it is "what would the model predict in a world where seasonality information were not available, all else equal." That is a do-statement on the model's inputs, not an observational analysis. The result tells you whether your model's confidence is about the world or about the calendar.
- Exclusions: Real logistics dataset acquisition; adversarial validation beyond one-sentence description; Population Stability Index implementation.
- Score: 9/10

## Candidate 03 — "Build an LLM Causal Reasoning Router with Claude Code: Which Rung Is This Question?"
- Source: causal-inference-with-case-studies/chapters/10-chapter-llms-causal-reasoning.md + chapters/21-case-llm-aegis-routing.md
- Lane: BUILD (Claude Code)
- Hook: The hospital spent $2.3M based on a model that confused correlation with intervention. The model answered fluently, confidently, and wrong. What if the architecture routed Rung 2+ questions to a tool that could actually handle them — instead of answering them as if they were Rung 1?
- The artifact: a Python CLI (~35 lines) implementing a causal query router: (1) takes a natural-language question as input, (2) calls Claude to classify it as Rung 1 (observational) / Rung 2 (interventional) / Rung 3 (counterfactual), (3) for Rung 1: routes to a simple statistical summary chain; for Rung 2: routes to a DAG-required chain that demands a structural causal model before answering; for Rung 3: routes to a potential-outcomes chain that makes the comparison-to-what explicit — printed as an annotated routing decision with the appropriate response strategy displayed.
- Prompt seed: `claude "Build a Python causal query router CLI. Input: a natural-language causal question. Use the anthropic SDK to: (1) classify the question as Rung 1 (observational/associational), Rung 2 (interventional — 'if we do X'), or Rung 3 (counterfactual — 'would this person have..if'); (2) based on rung, generate a response strategy: Rung 1 → direct statistical answer; Rung 2 → require a causal DAG and identify what structural assumptions are needed; Rung 3 → require the comparison individual and the counterfactual world specification. Print the rung classification, the routing decision, and the response strategy as a structured terminal output."`
- Read / check: CODE: verify rung classification is prompt-sensitive — "what fraction of patients recover?" correctly routes to Rung 1; "if we give drug X, will they recover?" to Rung 2; "would this patient have recovered if..." to Rung 3. Verify the Rung 2 chain correctly refuses to produce a causal estimate without structural assumptions. OUTPUT: the routing decision for Rung 2 should explicitly name the missing structural assumption (the DAG), not just hedge vaguely.
- Human supplies: Nothing — fully synthetic. The router works on any question the user types. The human provides the DAG if they want a Rung 2 question actually answered.
- Output medium: screen-recording mp4 (terminal showing three questions being routed: one per rung — each displaying its rung classification, routing arrow to the appropriate chain, and the response strategy or structural-assumption request printed in formatted output)
- The change: Add a "prompt sensitivity test" — submit the same Rung 2 question twice with slightly different wording (one more confidently causal, one more hedged) and show whether the model's rung classification is stable. The chapter uses prompt sensitivity as an instrument to distinguish genuine structural reasoning from trained hedging behavior.
- Teardown angle: The model's fluency is not the problem. The problem is the architecture that routes all questions to the same answer generator regardless of which rung they live on. A router that demands structural inputs for Rung 2+ questions is not a limitation — it is the discipline that prevents the $2.3M mistake.
- Exclusions: Full DAG encoding into the router; downstream causal estimation pipeline; multi-turn conversation state management.
- Score: 9/10

## Candidate 04 — "Build a GhostTrack Spotify DAG Builder with Claude Code"
- Source: causal-inference-with-case-studies/chapters/23-case-dag-ghosttrack-spotify.md
- Lane: BUILD (Claude Code)
- Hook: A music recommender flags songs with rising play counts as evidence of organic virality. But play count and feature placement both respond to the same hidden variable: editorial promotion. If you can't condition on what you can't see, can you at least know that you're missing it?
- The artifact: a Python script (~35 lines) that: (1) generates a synthetic Spotify-style dataset (track features, placement_flag, play_count, viral_flag) with a latent promotion variable driving both placement and plays, (2) uses Claude to generate a plausible DAG for the "virality recommendation" problem (what causes what?), (3) runs the back-door criterion on the proposed DAG to check whether the effect of organic features on virality is identified or unidentified (because promotion is unobserved), (4) produces a Manim animated DAG showing the unidentified back-door path highlighted in red.
- Prompt seed: `claude "Build a Python causal analysis of a Spotify virality case. (1) Generate N=5000 synthetic tracks with: organic_features (tempo, energy, valence as 3 floats), latent_promotion (binary, unobserved, prob 0.15), placement_flag = 1 if promotion or organic_features.sum()>threshold, play_count influenced by promotion (5x multiplier) and organic_features and noise, viral_flag = 1 if play_count > 95th percentile. (2) Call Claude via anthropic SDK to propose a DAG as an edge list for 'what causes virality' in this setting. (3) Run the back-door criterion: can the effect of organic_features on viral_flag be identified? (4) Generate a Manim DAG scene marking the unidentified back-door path through latent_promotion in red."`
- Read / check: CODE: verify that latent_promotion is never passed to the back-door criterion solver (simulating unobservability); verify the criterion correctly reports "unidentified" because no measured variable blocks the back-door path through promotion. OUTPUT: the Manim DAG should show organic_features → viral_flag (causal path, green) and organic_features ← promotion → play_count → viral_flag (back-door path through latent promotion, red and marked "unblocked").
- Human supplies: Nothing — fully synthetic. The script generates its own synthetic Spotify-style data. The human optionally uses real playlist/feature data from the Spotify API for a more authentic demonstration, but the synthetic version correctly illustrates the confounding structure.
- Output medium: Manim (animated DAG: nodes appear and edge arrows draw in; causal path from organic_features to viral_flag lights green; back-door path through latent_promotion lights red with "UNOBSERVED" label; back-door criterion verdict displays: "Effect NOT identified — promotion confounder unmeasured")
- The change: Demonstrate the instrumental variable approach: add a label_rotation_policy variable (exogenous — determined by label release schedule, affects placement but not organic quality) and show how this instrument could be used to identify the effect of organic features, even with promotion unmeasured.
- Teardown angle: The recommender is tracking promotion, not virality. The same features that look like virality signals are responses to editorial decisions the model cannot see. The DAG makes this visible — and makes the implicit assumption explicit: to claim organic features cause plays, you must close the back-door path through promotion. If promotion is unobserved, you can't. The model may be confidently tracking the wrong thing.
- Exclusions: Full IV estimation (2SLS); natural language processing of track lyrics for organic features; playlist sequence models.
- Score: 8/10

## Candidate 05 — "Build a Sensitivity Analysis for Observational Studies with Claude Code: VISAmatch Case"
- Source: causal-inference-with-case-studies/chapters/22-case-sensitivity-visamatch.md
- Lane: BUILD (Claude Code)
- Hook: An observational study shows that visa applicants who received coaching were 30% more likely to be approved. Is that coaching effect real — or is the effect entirely explained by unmeasured motivation? The chapter has a method for quantifying exactly how fragile the result is.
- The artifact: a Python script (~35 lines) that: (1) generates a synthetic visa application dataset (coaching_received, motivation_unmeasured, approval_outcome) with a confounded coaching effect, (2) runs a naive logistic regression and computes the naive ATE, (3) implements the E-value calculation (how strong would an unmeasured confounder have to be to explain away the result?), (4) calls Claude to interpret the E-value in one sentence for a non-expert, (5) generates a Manim sensitivity curve showing the ATE collapsing as unmeasured confounding strength increases.
- Prompt seed: `claude "Build a Python sensitivity analysis tool for a visa coaching observational study. (1) Generate N=3000 applicants: motivation (latent, U[0,1]), coaching = 1 if motivation > 0.5 or random(0.2); approval = logistic(1.5*coaching + 2*motivation + noise). (2) Fit LogisticRegression with only coaching observed (not motivation). Compute naive OR for coaching. (3) Compute the E-value: minimum OR an unmeasured confounder would need with both coaching and approval to fully explain the observed OR. (4) Call Claude via anthropic SDK to interpret the E-value in one sentence for a clinician. (5) Generate a Manim scene of the sensitivity curve."`
- Read / check: CODE: verify the E-value formula is correct: E = OR + sqrt(OR * (OR - 1)) for OR > 1; verify the naive OR correctly overestimates the true effect (because motivation is unobserved). OUTPUT: Manim sensitivity curve should show the adjusted OR starting at the naive value and declining toward null as unmeasured confounding strength increases; the E-value should be marked as the confounding strength where the OR crosses the null.
- Human supplies: Nothing — fully synthetic. The script generates its own data with known ground truth. The human optionally supplies real coaching program data to compute a genuine E-value, but the synthetic version illustrates the mechanism.
- Output medium: Manim (animated sensitivity curve: x-axis = unmeasured confounding strength (E), y-axis = adjusted odds ratio; line declining from naive OR toward null as E increases; dashed vertical line at E-value marked "confounder would need to be this strong"; horizontal dashed line at OR=1 labeled "null effect")
- The change: Compare two observational studies with the same point estimate: one with E-value = 1.5 (fragile — a modest confounder explains it away) and one with E-value = 3.2 (robust — would require a very strong unmeasured confounder). Show both sensitivity curves on the same axes to demonstrate that identical point estimates can have radically different fragility.
- Teardown angle: Every observational estimate is conditional on having measured the right confounders. The E-value quantifies the assumption you can't test — and makes visible whether your conclusion is robust or hanging by a thread. The visa coaching result is only real if no unmeasured variable could plausibly have an E-value above the threshold. Whether that's plausible is a domain-knowledge question, not a statistical one.
- Exclusions: Rosenbaum bounds (alternative sensitivity measure); full propensity score matching implementation; bootstrap confidence intervals for E-values.
- Score: 9/10

## Candidate 07 — "Build a Causal Agent Supply Chain Risk Monitor with Claude Code"

- Lane: BUILD (Claude Code)

- The artifact: a Python CLI (~40 lines) implementing a two-stage causal agent: (1) Stage 1 — receive a supplier alert (text description of the risk signal), call Claude to classify whether the alert is "regime-confounded" (sensor anomaly from operating context), "genuine operational stress" (upstream cause of the signal), or "unknown" (insufficient information to classify), (2) Stage 2 — if classified as genuine stress, call Claude to propose an intervention (expedite from backup supplier, increase safety stock, notify logistics); if regime-confounded, call Claude to propose a diagnostic (check operating regime, request follow-up measurement) — printed as a structured decision tree output.

Stage 1: call Claude via anthropic SDK to classify the alert as 'regime-confounded' (sensor artifact from operating context), 'genuine operational stress' (real upstream cause), or 'unknown'. Stage 2: based on classification — if genuine, propose a supply chain intervention (which backup, how much safety stock, who to notify); if regime-confounded, propose a diagnostic action (which operating regime to check, what measurement to request, when to re-evaluate). - Human supplies: Sample alert text descriptions. The agent works on any text input; for a production version, the human would supply an alert API feed from their actual supply chain monitoring system.
- Output medium: screen-recording mp4 (terminal showing two alerts processed: one regime-confounded (diagnostic path) and one genuine stress (intervention path) — with the two-stage decision tree printing in real time, showing how the causal classification changes the agent's action)
- The change: Add a "confidence threshold" gate: if the Stage 1 classification confidence is below 70%, the agent routes to "human-in-the-loop" mode — printing a request for human verification before proceeding — demonstrating that the agent knows the boundaries of its own causal reasoning.
- Teardown angle: The agent that acts on every alert is not more responsive — it is less reliable. The causal classification step is what separates a responsive agent from an autonomous one that amplifies false alarms. The Milford Haven lesson: the cost of over-alerting is that operators stop responding to alerts entirely.
- Exclusions: Full reinforcement learning agent implementation; real supply chain API integration; multi-agent coordination across suppliers.
- Score: 8/10

## Candidate 08 — "Build a Confounding Audit Tool for Machine Learning Models with Claude Code"
- Source: causal-inference-with-case-studies/chapters/12-specification_bottleneck.md
- Lane: BUILD (Claude Code)
- Hook: A machine learning model achieves 95% accuracy. But it learned a confounded feature — one that correlates with the label in training data because of how the data was collected, not because of any causal relationship. How do you know if your model is tracking the signal or the confounder?
- The artifact: a Python script (~35 lines) that: (1) trains a simple classification model (logistic regression or gradient boosted trees) on a synthetic dataset with an injected confounder (a feature that correlates with the label only because of data collection bias), (2) computes SHAP feature importance, (3) calls Claude with the feature importance list and a domain description to classify each feature as "causally plausible" or "likely spurious/confounded" with one-sentence rationale, (4) generates a Manim animated SHAP bar chart with each bar color-coded by Claude's causal classification.
- Prompt seed: `claude "Build a Python confounding audit for an ML classifier. (1) Generate N=5000 examples: true_signal (U[0,1]), spurious_confounder (corr 0.7 with label only due to data collection, not causation), label = sigmoid(2*true_signal + noise) > 0.5. (2) Train LogisticRegression on both features. (3) Compute SHAP values. (4) Call Claude via anthropic SDK with feature names + SHAP values + domain description; ask Claude to classify each feature as causally plausible, likely spurious, or unknown with rationale. (5) Generate a Manim bar chart of SHAP values color-coded by causal plausibility."`
- Read / check: CODE: verify the spurious confounder has genuine SHAP importance in the trained model (the model should learn it because it correlates with the label in-distribution even though it's causally inert); verify the causal audit correctly flags it as spurious. OUTPUT: Manim chart should show spurious_confounder bar in orange (likely spurious) and true_signal bar in green (causally plausible) — making the causal vs. statistical feature importance distinction visually immediate.
- Human supplies: A domain description for the specific ML task (e.g., "predicting loan default — the spurious feature is 'zip code', which correlates with default in historical data due to discriminatory lending practices, not causal factors"). Without a real domain description, the synthetic example illustrates the mechanism but lacks the interpretive depth.
- Output medium: Manim (animated SHAP bar chart: bars appear in descending importance order; Claude's causal classification revealed as color fill — green for plausible, orange for spurious, gray for unknown; a text annotation: "High SHAP ≠ Causal feature")
- The change: Add a "model audit" step: retrain the model on the causally plausible features only and compare accuracy in-distribution (similar) vs. out-of-distribution (spurious features shift distribution, causally plausible features remain stable) — demonstrating that the spurious features produce fragile models.
- Teardown angle: SHAP importance is a statistical measure, not a causal one. A feature can have high importance because it genuinely causes the outcome, or because it correlates with the outcome through a confounded data-collection process that won't hold at deployment. Only the causal question — would intervening on this feature change the outcome? — separates the two. The model audit makes that question answerable before deployment, not after.
- Exclusions: Full causal discovery on the feature set; domain adaptation techniques; fairness/bias auditing beyond confounding identification.
- Score: 8/10
